# 제품 도메인 ERD 정규화 방향 정리

## ✅ 효능과 성분-효능 테이블

**도메인:** 상품 / 추천

**대상 테이블:** `effects`, `ingredient_effects`

### 기존 역할

`effects` 테이블은 보습, 진정, 미백, 각질 케어, 탄력 등 성분이 가질 수 있는 효능 값을 저장한다.

`ingredient_effects` 테이블은 성분과 효능을 연결하여, 특정 성분이 어떤 효능과 관련 있는지 관리한다.

### 변경 후 역할

MVP 단계에서는 `effects`, `ingredient_effects` 테이블을 사용하지 않고 보류한다.

성분과 효능의 관계를 DB에 저장하지 않고, 피부 고민별 추천 성분 매핑을 백엔드 코드에서 관리한다. 상품 추천은 사용자가 선택한 피부 고민에 해당하는 추천 성분 목록과 상품의 대표 성분을 직접 비교하는 방식으로 처리한다.

### 변경 내용

- `effects` 테이블을 MVP에서 보류합니다.

  기존에는 성분의 효능을 별도 테이블로 관리하여 추천 근거를 세분화하려는 목적이 있었습니다. 하지만 MVP에서는 피부 고민별 추천 성분 목록을 코드로 관리하고, 상품의 대표 성분과 직접 매칭하는 방식으로도 추천 기능 구현이 가능합니다. 따라서 효능 값을 별도 테이블로 관리하는 구조는 MVP 기준에서 필수적이지 않다고 판단했습니다.

- `ingredient_effects` 테이블을 MVP에서 보류합니다.

  한 성분이 여러 효능을 가질 수 있다는 점에서는 의미가 있지만, MVP 추천 흐름은 “피부 고민 → 추천 성분 → 상품” 구조로 처리합니다. 따라서 성분과 효능을 한 번 더 연결하는 중간 테이블은 초기 구현에서는 복잡도를 높일 수 있어 보류합니다.

- 피부 고민별 추천 성분 매핑을 코드로 관리합니다.

  사용자가 선택한 피부 고민에 따라 추천에 사용할 성분 목록을 아래와 같이 정의합니다.

| 고민 코드 | 고민 / 역할 | 추천 성분 |
| --- | --- | --- |
| `MOISTURE` | 수분 / 보습 | 글리세린, 히알루론산, 저분자 히알루론산, 베타인, 판테놀, 세라마이드, 스쿠알란, 시어버터 |
| `SOOTHING` | 피부 진정 / 민감 / 붉은기 | 병풀추출물, 시카, 어성초추출물, 티트리, 알란토인, 판테놀, 마데카소사이드, 쑥추출물 |
| `BRIGHTENING` | 피부톤 불균형 / 잡티 / 칙칙함 | 나이아신아마이드, 비타민 C, 비타민 C 유도체, 트라넥사믹애씨드, 알부틴 |
| `TEXTURE_PORE` | 피부결 / 모공 / 각질 | AHA, BHA, PHA, 위치하젤, 레티놀, 징크 PCA, 발효성분, 갈락토미세스, 비피다발효용해물, 나이아신아마이드 |
| `ANTI_AGING` | 노화 / 탄력 / 주름 | 레티놀, 펩타이드, 아데노신, 나이아신아마이드, 발효성분, 비피다발효용해물, 세라마이드 |

- 추천 후보는 매칭 성분 기준으로 선정합니다.

  사용자가 선택한 피부 고민의 추천 성분 목록과 상품의 대표 성분을 비교합니다. 겹치는 성분이 하나 이상 있는 상품을 추천 후보로 선정합니다.

  예를 들어 사용자가 `MOISTURE`를 선택한 경우, 추천 성분은 글리세린, 히알루론산, 판테놀, 베타인 등이 됩니다.

  라운드랩 1025 독도 토너의 대표 성분이 글리세린, 판테놀, 알란토인, 베타인이라면 글리세린, 판테놀, 베타인이 매칭되므로 추천 후보가 됩니다.

- 추천 이유는 매칭 성분 기반 템플릿으로 생성합니다.

  효능 테이블이나 성분 설명 필드를 사용하지 않고, 사용자 고민과 매칭 성분을 기반으로 추천 이유를 생성합니다.

  기본 템플릿:  
  `{고민명} 고민에 맞는 {매칭성분} 성분이 포함되어 있어 추천했어요.`

  예시:  
  `수분 / 보습 고민에 맞는 글리세린, 판테놀, 베타인 성분이 포함되어 있어 추천했어요.`

  예시:  
  `피부 진정 / 민감 / 붉은기 고민에 맞는 병풀추출물, 판테놀, 알란토인 성분이 포함되어 있어 추천했어요.`

### 사용되는 화면

추천 결과 화면, 상품 상세 화면

### 사용되는 기능

상품 추천, 성분 매칭, 추천 이유 생성

### 관련 테이블

`products`, `ingredients`, `product_ingredients`, `recommendation_products`

### 추후 확장 가능성

추후 추천 이유를 더 정교하게 제공하거나, 성분별 효능을 관리자 페이지에서 관리해야 하는 경우 `effects`, `ingredient_effects` 테이블을 다시 도입할 수 있습니다.

또한 성분과 효능의 관계를 DB에서 관리하게 되면, “판테놀 → 보습/진정”, “나이아신아마이드 → 미백/피지/탄력”처럼 하나의 성분이 여러 효능을 가지는 구조를 명확하게 표현할 수 있습니다. LLM을 활용한 추천 이유 생성을 활용할 수 도 있습니다.

## ✅ 성분 테이블

**도메인:** 상품 / 추천

**대상 테이블:** `ingredients`

### 기존 역할

`ingredients` 테이블은 화장품 성분 정보를 저장한다.

### 변경 후 역할

전과 동일하게 성분 정보를 저장하되, MVP 단계에서는 추천 성분 매칭에 필요한 성분명과 관리자용 설명을 관리한다.

### 변경 내용

- 성분명에는 유니크 제약 조건을 적용합니다.

  같은 성분이 중복 저장되면 추천 매칭 결과가 흔들릴 수 있으므로, `name` 컬럼은 중복되지 않도록 관리합니다.

- 설명 필드를 유지합니다.

  `description`은 추천 이유 생성에는 사용하지 않고, 관리자용 성분 설명 또는 내부 관리 메모 용도로 사용합니다. 하나의 성분이 여러 효능에 걸칠 수 있으므로, 사용자에게 보여주는 추천 이유는 성분 설명을 그대로 사용하지 않고 사용자 고민과 매칭 성분 기반 템플릿으로 생성합니다.

- 주의 성분 여부 컬럼을 삭제 합니다.

  기존 `is_caution` 컬럼은 성분 자체가 주의 성분인지 여부를 boolean 값으로 관리하려는 목적이 있었습니다. 하지만 사용자의 불편 경험은 유형마다 제외해야 하는 성분이 다릅니다. 예를 들어 각질 케어 제품이 불편했던 경우에는 AHA, BHA, PHA를 제외하고, 오일감이 많은 제품이 불편했던 경우도 이와 마찬가지 입니다.

  따라서 MVP에서는 모든 주의 성분을 하나의 boolean 값으로 관리하지 않고, 불편 경험별 제외 성분 목록을 백엔드 코드에서 관리하는 방식으로 처리합니다.

- 불편 경험별 제외 성분 매핑을 코드로 관리합니다.

  사용자가 선택한 불편 경험에 따라 제외할 성분 목록을 아래와 같이 정의합니다.

| 설문 코드 | 사용자 선택 | 제외 기준 |
| --- | --- | --- |
| `STINGING_SENSITIVE` | 바를 때 따갑거나 화끈거렸던 제품 | AHA, BHA, PHA, 레티놀, 비타민 C, 비타민 C 유도체, 티트리 포함 상품 제외 |
| `HEAVY_OIL_SENSITIVE` | 오일감이 많은 제품 | 시어버터 또는 스쿠알란 포함 상품 제외 |
| `EXFOLIANT_SENSITIVE` | 각질 케어 제품 AHA/BHA | AHA, BHA, PHA 포함 상품 제외 |

### 사용되는 화면

관리자 성분 관리 화면, 추천 결과 화면, 상품 상세 화면

### 사용되는 기능

성분 정보 관리, 상품 성분 표시, 피부 고민별 성분 매칭, 불편 경험 기반 상품 제외, 추천 이유 생성

### 관련 테이블

`products`, `product_ingredients`

### 추후 확장 가능성

추후 성분별 효능을 정교하게 관리해야 하는 경우 `effects`, `ingredient_effects` 테이블을 다시 검토할 수 있습니다.

또한 불편 경험별 제외 성분을 관리자 페이지에서 관리해야 하는 경우, `is_caution` boolean이 아니라 `caution_type` 또는 별도 주의 성분 매핑 테이블을 도입하는 방식을 검토할 수 있습니다.

## ✅ 상품-성분 테이블

**도메인:** 상품 / 추천

**대상 테이블:** `product_ingredients`

### 기존 역할

`product_ingredients` 테이블은 상품과 성분의 관계를 저장한다.

하나의 상품은 여러 성분을 가질 수 있고, 하나의 성분도 여러 상품에 포함될 수 있으므로 상품과 성분의 N:M 관계를 관리하는 중간 테이블 역할을 한다.

### 변경 후 역할

전과 동일하게 상품과 성분의 관계를 저장한다.

다만 MVP 추천 로직에서는 성분 포함 여부만 사용하고, `display_order`는 추천 로직이 아니라 상품 상세 화면에서 대표 성분 노출 순서를 관리하는 용도로 사용한다.

### 변경 내용

- `display_order` 컬럼을 유지합니다.

  `display_order`는 추천 로직에서 상품 후보를 선정하는 데 직접 사용되지는 않습니다. 현재 추천 방식은 상품에 특정 성분이 포함되어 있는지 여부를 기준으로 처리하기 때문입니다.

  다만 상품 상세 화면이나 추천 결과 화면에서 대표 성분을 데이터셋에 입력된 순서대로 보여줄 필요가 있으므로, 성분 노출 순서를 관리하기 위한 용도로 유지합니다.

## ✅ 상품 테이블

**도메인:** 상품

**대상 테이블:** products

### 기존 역할

화장품 상품의 기본 정보를 저장한다.

### 변경 후 역할

전과 동일

### 변경 내용

- 외부 네이버 상품 ID 컬럼을 추가했습니다.  
  네이버 쇼핑 API에서 제공하는 상품 ID를 저장하여, 추후 동일 상품 중복 저장 여부를 판별하거나 외부 상품 정보를 갱신할 때 기준값으로 활용할 수 있습니다.

- 제품명 컬럼명을 상품명 컬럼명으로 변경했습니다.  
  실제 화면과 서비스 내 표현이 “상품” 기준으로 사용되므로, 용어를 통일하기 위해 컬럼명을 변경했습니다.

- 설명 필드를 삭제했습니다.  
  기존 설명 필드는 추천 결과에서 상품 설명 또는 추천 이유를 보여주는 용도로 사용될 수 있었지만, 정적인 설명 문구는 사용자별 추천 맥락을 충분히 반영하기 어렵우며 획일화 된다고 판단했습니다. 추후 추천 이유가 필요할 경우 “사용자 고민”, “피부 타입”, “매칭 성분/속성”을 기반으로 LLM을 사용해 동적으로 생성하는 방식을 고려합니다.

- 평점 컬럼과 리뷰 수 컬럼을 삭제했습니다.  
  현재 연동한 네이버 쇼핑 API 응답에서는 평점과 리뷰 수를 제공하지 않으므로, MVP 단계에서는 해당 컬럼을 제외합니다. 추후 리뷰 데이터 연동 또는 별도 사용자 피드백 기능이 필요해질 경우 다시 검토합니다.

### 사용되는 화면

추천 결과 화면, 상품 상세 화면

### 사용되는 기능

상품 추천, 상품 상세 조회, 네이버 쇼핑 정보 표시

### 추후 확장 가능성

## ✅ 상품-태그와 태그 테이블

**도메인:** 추천 / 설문

**대상 테이블:** `tags`, `product_tags`

### 기존 역할

`tags` 테이블은 피부 고민, 피부 타입, 민감 경험, 선호 제품군 등 여러 도메인에서 공통으로 사용할 수 있는 태그 값을 저장한다.

`product_tags` 테이블은 상품과 태그를 연결하여, 특정 상품이 어떤 피부 고민이나 제품 속성과 관련 있는지 관리한다.

### 변경 후 역할

MVP 단계에서는 `tags`, `product_tags` 테이블을 사용하지 않고 보류한다.

설문 선택값은 `survey_options.option_code`로 관리하고, 상품 분류는 `products.category`로 관리한다. 상품 추천은 별도 태그 연결이 아니라 상품의 카테고리와 성분 정보를 기반으로 백엔드 추천 로직에서 처리한다.

### 변경 내용

- `tags` 테이블을 MVP에서 제외 또는 보류합니다.

  기존에는 피부 고민, 피부 타입, 민감 경험, 선호 제품군 등을 공통 태그로 관리하려는 목적이 있었지만, 현재 MVP에서는 해당 값들이 비교적 고정되어 있어 별도 태그 테이블 없이 `survey_options.option_code`와 enum/Map 기반 로직으로 관리할 수 있다고 판단했습니다.

- `product_tags` 테이블을 MVP에서 제외 또는 보류합니다.

  기존에는 상품에 `MOISTURE`, `SOOTHING`, `TONER` 같은 태그를 부여해 추천에 활용하려는 구조였지만, 현재 추천 방식은 태그 기반이 아니라 `products.category`와 `product_ingredients`, `ingredients`를 활용한 성분 매칭 방식입니다. 따라서 상품별 태그를 별도로 저장하는 구조는 MVP 기준에서 중복 관리가 될 수 있다고 판단했습니다.

- `survey_options.tag_id` 연결을 제거합니다.

  설문 선택지가 어떤 의미를 가지는지는 `tags`를 거치지 않고 `option_code`로 직접 관리합니다. 예를 들어 `MOISTURE`, `DRY`, `TONER`, `EXFOLIANT_SENSITIVE` 같은 코드를 설문 옵션에 직접 저장하고, 추천 로직에서 해당 코드를 해석합니다.

- 상품과 설문 선택지는 직접 연결하지 않습니다.

  설문 선택값과 상품 데이터를 DB 관계로 직접 연결하지 않고, 백엔드 추천 로직에서 `option_code`를 해석해 상품의 `category`와 대표 성분을 비교합니다.
